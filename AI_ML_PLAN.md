# AI and Machine Learning Plan

## Purpose

Explore whether software can help reviewers notice unusual changes in a person's recorded measurements. The feature is experimental decision support, not a diagnostic or treatment system.

## Build order

### Stage 1 — Data validation
- Check type, unit, timestamp, missing values, duplicates, and impossible formats.
- Keep the original observation available for review.
- Do not silently alter a measurement to make it fit a model.

### Stage 2 — Transparent rules
Implement small, documented rules such as:
- Missing or stale observation.
- Sudden change relative to a configured personal baseline.
- Value outside a deliberately configured demo range.

Ranges must be selected from an authorized specification or clearly labelled as illustrative demo rules. Do not invent medical thresholds or present example rules as clinical standards.

Each flag should include:
- Rule ID and version.
- Input observations used.
- Reason in plain language.
- Time of evaluation.
- A statement that it needs human review.

### Stage 3 — Optional anomaly detection
Only add a model if there is sufficient suitable data and time. Possible exploratory methods include:
- Rolling statistics or robust z-scores for simple baselines.
- Isolation Forest for exploratory multivariate anomaly detection.
- Scikit-learn preprocessing pipelines for repeatable experiments.

A model trained only on synthetic examples cannot establish real-world medical performance. Never claim clinical accuracy from a toy dataset.

## Data requirements

Document:
- Data source and permission.
- Whether data is synthetic, public, or authorized.
- Measurement definitions and units.
- Sampling frequency and missingness.
- Subject-level separation for evaluation.
- Known bias and limitations.

Avoid using identifiable health data without appropriate authorization and safeguards.

## Evaluation

For a labelled dataset, consider:
- Precision and recall.
- False-positive and false-negative rates.
- Confusion matrix.
- Performance across relevant subgroups when data and permissions support it.
- Robustness to missing, delayed, duplicated, and noisy measurements.

For unlabelled synthetic data, report only limited exploratory behavior and do not imply verified detection accuracy.

## Explainability and UI

Use language such as:
- “Review suggested: measurement differs from this profile's recent baseline.”
- “Data may be stale: no recent observation received.”
- “This flag is generated by an experimental rule and is not a diagnosis.”

Show the timestamp, unit, baseline window, rule/model version, and data-quality caveats when relevant.

## Safety constraints

- Do not recommend medication or treatment.
- Do not use alerts as a substitute for mission medical procedures.
- Do not present an anomaly score as a probability of disease unless appropriately validated for that exact interpretation.
- Do not hide uncertainty.
- Provide a way to inspect the source measurements.
- Keep rules and models versioned and tested.

## MVP decision

**Recommended for the hackathon:** implement transparent rules and charts first. Add an optional ML experiment only after the basic data flow and offline behavior work reliably.
